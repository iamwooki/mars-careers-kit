# 지원서 파이프라인 (job-apply)

공고 + 문항이라는 **두 입력**을 받아 제출 직전 상태의 자소서와 분석보고서를 만든다.
career-orchestrator의 Phase 3~4를 지원서 한 건 단위로 표준화한 것이다.

**실행 모드: 서브 에이전트 순차 파이프라인** (파일 기반 전달). 단계마다 산출물이 파일로 고정되고
다음 단계의 입력이 되므로 팀 통신이 필요 없다. 모든 `Agent` 호출은 `model: "opus"`.
사용자와 대화가 필요한 게이트(재료 확인·수치 사용 가부)는 메인 세션이 직접 처리한다.

## 디렉토리 규약

```
applications/{지원처}_{직무}/
├── 00_input.md              # 입력 정규화 (assets/00_input_template.md 양식)
├── raw/                     # 공고 원문 (pdf/txt/이미지) — 그대로 보존
├── 00_target.md             # 직무 분석·매칭·지원 가부·문항-카드 매핑 (career-analyst)
├── 01_resume_draft.md       # 초안 (resume-writer)
├── 01_resume_draft_v2.md…   # 검수 반영 개정판 (번호 증가, 이전 판 보존)
├── 02_resume_final.md       # 제출본 (사용자 확인 후 확정)
├── 03_*.md                  # 학습 가이드 등 부속 산출물 (선택)
└── {지원처}_분석보고서.html   # scripts/build_report.py 생성물 — 직접 수정 금지
_workspace/review_{지원처}_{차수}.md   # 검수 리포트 (사실 검수 / 심사관 검수)
_workspace/backlog_사용자입력_{날짜}.md # 사용자가 채워야 할 목록
applications/지원현황.yaml → 지원현황.html  # 지원·결과 원장 (Phase 8, build_tracker.py)
```

## Phase 0. 컨텍스트 확인 (메인)

1. `applications/{지원처}_*/`가 이미 있으면 **후속 실행**: 사용자 요청이 지목한 단계만 재실행한다
   (문항 수정 → Phase 4부터, 검수만 → Phase 5, 보고서만 → Phase 7).
2. 없으면 **신규 실행**: Phase 1부터.
3. `inventory/` 카드 수와 confirmed 비율을 세어 둔다. confirmed가 0이면 결과물이 전부
   "확인 필요" 표시를 달고 나가므로 사용자에게 미리 알린다.

## Phase 1. 입력 정규화 (메인)

사용자가 준 것을 `00_input.md`로 옮겨 적는다 (양식: `assets/00_input_template.md`).
PDF는 텍스트를 추출해 `raw/`에 함께 둔다. 반드시 채울 항목:

- 기관·직무·채용인원·전형 절차·마감일
- **수행직무**(공고의 직무 목록 원문), **지원자격**(경력 연수·학위·자격 필수 요건), 우대사항
- **문항 원문 + 글자수 범위 + 공백 포함/제외 기준 + 줄바꿈·소제목 허용 여부**
- 사용자가 아직 모르는 항목은 `[확인 필요]`로 남긴다. 특히 글자수 기준과 경력 인정 범위는
  나중에 통째로 다시 쓰게 만드는 항목이라 비워 두더라도 표시는 반드시 한다.

## Phase 2. 직무 분석·매칭 (career-analyst 서브 에이전트)

입력: `00_input.md`, `inventory/*.md`, `profile.md`. 출력: `00_target.md`.
구조는 `references/target-analysis-outline.md`를 따른다. 핵심은 세 가지다.

- **회사의 서비스를 먼저 검색한다 (지원동기의 재료).** 공고만 보지 말고 WebSearch/WebFetch로 그 회사가 실제로 운영하는
  서비스·제품·시스템·최근 사업(보도자료, 홈페이지 사업소개, 연차보고서)을 찾아 `00_target.md`에 "기관 서비스 조사" 절로 정리한다
  (서비스명 / 무엇을 하는 것인지 한 줄 / 출처 URL·확인일). 이어서 **사용자의 직무·경험과 맞닿는 서비스 2~3개**를 골라
  "어느 카드의 어떤 경험이 이 서비스의 어떤 일과 닮았는지"를 적는다. 검색으로 확인하지 못한 내용은 쓰지 않고, 회사 내부 사정을 추측하지 않는다.
- **직무 해설을 비유와 장면으로 쓴다.** 처음 보는 직무라도 사용자가 "이 자리가 뭘 하는 자리인지"
  이해해야 면접에서 직무 언어로 말할 수 있다.
- **지원자격을 가장 먼저 판정한다.** 경력 연수·필수 자격이 안 맞으면 나머지 분석은 무의미하다.
  경력 연수는 카드의 기간을 실제로 합산하고, 공고 각주의 "관련 업무" 정의와 대조한다.
- **갭은 "근거 없음"으로 정직하게 쓴다.** 카드에 없는 역량을 있다고 쓰면 자소서까지 오염된다.
  갭마다 [지식형: 단기 학습 가능 / 경험형: 단기 보완 불가]를 구분하고 보완 제안을 붙인다.

## Phase 3. 재료 확인 게이트 (메인)

`00_target.md`의 "확인 필요"와 카드의 `[인터뷰 필요]` 중 **이 지원서에 쓰일 카드**의 것만 골라
`_workspace/backlog_사용자입력_{날짜}.md`에 우선순위(제출 차단 / 수치 사용 가부 / 보강 / 기타)로
정리해 사용자에게 보여 준다. 답을 기다리느라 멈추지 않는다 — 초안은 `[확인 필요]` 표시를
달고 진행하고, 답이 오면 Phase 6에서 반영한다.

## Phase 3.5. 경험 추천 → 사용자 조합 (기본 경로)

초안을 바로 쓰지 않는다. **연관된 경험을 먼저 추천하고, 사용자가 고민해서 조합한 뒤에 쓴다.**
(자동으로 쓴 초안은 결국 제출 화면에서 본인이 다시 쓰게 된다. 본인이 고른 재료로 쓴 글이 본인 말로 남고, 면접에서도 버틴다.)

1. career-analyst(또는 메인)가 `assets/00_materials_template.md` 양식으로 `00_materials.md`를 만든다.
   문항마다 **후보 경험 3~5개**를 적합도순으로 놓고, 후보별로 [한 줄 요약 / 이 문항에 맞는 이유 /
   쓸 수 있는 사실·수치 / 약점·면접 리스크 / 필요 분량]을 적는다. 이어서 **조합안 2개(A·B)**와 추천을 붙인다.
   - **키워딩 먼저**: 문항마다 본문보다 먼저 **핵심 키워드 2~3개**(그 문항에서 심사관 머리에 남길 말 — 예: "같이 볼 근거", "끝까지 읽는 힘")와
     그 키워드를 한 줄로 묶은 **소제목 후보 2개**를 제시한다. 키워드는 공고의 직무 어휘와 사용자의 경험 양쪽에 걸쳐 있어야 한다.
     사용자가 키워드를 고르거나 고친 뒤에 그 키워드에 맞는 경험을 조합한다.
   - **지원동기 문항**은 00_target.md "기관 서비스 조사"에서 고른 서비스 2~3개를 후보와 함께 보여 준다
     (이 회사의 어떤 서비스가 내 어떤 경험과 맞는지 → 그래서 왜 이 회사인지).
   - 후보는 업무 카드만이 아니라 학부 프로젝트·교육·자격·사이드 프로젝트·profile.md/education.md 항목까지 넓게 본다.
   - 추천은 하되 결정하지 않는다. 약점을 숨기지 않는다(카드의 [인터뷰 필요], 남의 숫자로 읽힐 위험).
   - 마지막에 "전체 배치 점검"으로 문항 간 경합과 놀고 있는 강한 카드를 보여 준다.
2. 메인이 요약을 대화로 보여 주고 **사용자의 선택을 기다린다.** 이 게이트는 멈추는 게이트다.
   사용자는 "1번은 A안, 2번은 ①에 ③ 한 줄, 3번은 내가 쓴 메모로"처럼 답하면 된다. 사용자가 직접 쓴 문장·메모는
   그대로 재료로 쓰고, 표현을 임의로 바꾸지 않는다(다듬을 곳은 제안으로만).
3. 선택 결과를 `00_materials.md`의 [내 선택] 칸에 기록한 뒤 Phase 4로 간다. resume-writer는 **선택된 조합만** 쓴다.
   선택에 없는 카드를 끼워 넣지 않는다.

**자동 경로(건너뛰기)**: 사용자가 "바로 써줘/자동으로/시간 없어"라고 하거나 마감이 24시간 이내면
추천표는 만들되 기다리지 않고 추천안(각 문항의 추천 조합)으로 Phase 4를 진행한다. 이 경우 완료 보고에
"추천안으로 자동 진행 — 조합을 바꾸려면 00_materials.md의 다른 안을 지정"이라고 알린다.

## Phase 4. 초안 작성 (resume-writer 서브 에이전트)

resume-writing 스킬 원칙을 따른다. 입력은 `00_materials.md`의 [내 선택](없으면 추천안). 추가로 이 파이프라인에서 강제하는 것:

- **키워딩 → 본문**: 문항마다 확정된 키워드로 소제목(큰따옴표 한 줄)을 먼저 세우고, 본문의 모든 문단이 그 키워드로 돌아오게 쓴다.
  첫 문단에서 키워드를 자기 말로 정의하고, 마지막 문장에서 같은 키워드로 닫는다. 키워드와 무관한 경험은 아무리 좋아도 뺀다.
- **지원동기는 회사 서비스에서 출발**: "기관 서비스 조사"에서 확인한 실제 서비스·시스템 이름을 본문에 쓰고, 그것과 닿는 내 직무 경험을 짝지어 쓴다.
  설립연도·슬로건 같은 누구나 쓰는 문장은 쓰지 않는다.
- **입력 폼 주의**: 일부 채용 사이트 입력 폼은 가운뎃점(·)을 지운다(실제 제출본에서 확인된 사례). 붙여넣기용 본문에서는 가운뎃점 대신 쉼표나 "와/과"를 쓴다.
- **배치 원칙**: 직무적합성을 채점하는 문항(경력·성과 문항)에 가장 직무다운 카드를 배치한다.
  지원동기 문항에 최강 카드를 소진하면 심사관 검수에서 "배치 역전"으로 지적된다.
- **어휘 원칙**: 공고 수행직무의 명사를 문항 본문에 그대로 쓴다 (예: 사업비 산정 근거, 검수, 산출물).
  이전 직장의 내부 용어(위원회·TF·안건 등)는 1회 이하로 줄이고 직무 어휘로 번역한다.
- 문항 끝 주석에 사용 카드·수치 출처·`[확인 필요]`를 남긴다 (기존 규약 유지).
- 글자수는 `scripts/charcount.py`로 실측한다. 문항 헤딩에 `(300~750자)` 형식이 있으면 자동 인식.

## Phase 5. 이중 검수 (quality-reviewer 서브 에이전트 2회)

1. **사실 검수** — 카드 대조·글자수·요건. 출력 `_workspace/review_{지원처}_{n}차.md`.
2. **심사관 검수** — screener-review 스킬로 "떨어뜨리는 사람" 관점. 출력 `_workspace/review_{지원처}_심사관.md`.
   사실 검수가 "제출 가능"이라고 해도 심사관 검수가 "탈락 위험"이면 Phase 6으로 되돌린다.
   두 검수는 보는 것이 다르다: 사실 검수는 거짓을 잡고, 심사관 검수는 진실이어도 떨어지는 이유를 잡는다.

## Phase 6. 수정 (resume-writer 재호출, 최대 2라운드)

지적 반영본은 `01_resume_draft_v{n}.md`로 번호를 올려 저장한다 (이전 판 보존 — 어느 지적이
어떻게 반영됐는지 추적하기 위해). 사용자가 승인한 판을 `02_resume_final.md`로 복사한다.
심사관 검수의 "판정을 뒤집을 조건" 중 사용자 입력이 필요한 것은 【 】 자리표시로 남기고
제출 불가 상태임을 보고서에 명시한다.

## Phase 7. 분석보고서 HTML (스크립트)

```
python .claude/skills/job-apply/scripts/build_report.py applications/{지원처}_{직무}
```

`00_target.md` + 최신 자소서 + `_workspace/review_*{지원처}*.md`를 한 페이지로 묶는다.
HTML은 생성물이므로 직접 수정하지 않는다. 수정은 md에 하고 재빌드한다.
Chrome/Edge headless 스크린샷으로 렌더를 확인한다 (한글 폰트·표 넘침).

## Phase 8. 제출 기록·결과 추적 (메인)

사용자가 제출했다고 알리면(또는 결과가 나오면) `applications/지원현황.yaml`을 고치고 뷰어를 재생성한다.

```
python .claude/skills/job-apply/scripts/build_tracker.py .
```

- 제출 화면 PDF·캡처는 `applications/{지원처}_{직무}/05_제출본/{제출일}_{지원처}_제출본.pdf`로 보관하고 텍스트를 추출해 둔다.
  사용자가 제출 화면에서 문장을 고치는 일이 흔하므로 **실제 제출 문장은 05_제출본이 기준**이다(02_resume_final.md와 다를 수 있다).
- yaml에는 수험번호·제출일·전형 단계·결과·지원서에 적어 낸 값(희망연봉·경력 기간 표기 등)·면접 대비·회고를 적는다.
  **비밀번호는 적지 않는다.** 결과가 나오면 status·stages·timeline을 함께 고치고 lessons에 회고를 남긴다.
- 비공개 자료 — site/·cv.yaml 반입 금지.

## 완료 보고

1. 산출물 경로 2. 지원 가부 판정 한 줄 + 유사도 3. 사용 카드/제외 카드
4. **제출 차단 항목**(사용자 입력 필요) 5. 심사관 검수 판정 + 뒤집을 조건

## 테스트 시나리오
