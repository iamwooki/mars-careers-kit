# 경력 인벤토리 — STAR-I 프레임워크

## 목적

자소서·포트폴리오의 원천 데이터베이스를 만든다. 한 번 잘 정리해두면 지원처가 바뀔 때마다
글을 새로 쓰는 것이 아니라 **카드를 골라 재조합**하게 된다. 그래서 카드 하나하나는
특정 지원처에 맞추지 말고 사실 중심으로, 재사용 가능하게 기록한다.

## 3층 구조

| 층 | 파일 | 내용 |
|----|------|------|
| L1 커리어 테마 | `inventory/themes.md` | 나를 관통하는 핵심 역량 축 3~4개 (예: 업무자동화, 데이터 기반 개선, 협업 조율) |
| L2 프로젝트 카드 | `inventory/P##_슬러그.md` | 프로젝트/업무 1건 = 카드 1장 (STAR-I 구조) |
| L3 성과 뱅크 | `inventory/achievements.md` | 모든 카드에서 추출한 정량 성과 한 줄 목록 (자소서에 바로 인용) |

L1은 L2가 5장 이상 모인 뒤에 도출한다 — 테마를 먼저 정하면 카드가 테마에 끼워맞춰져 왜곡된다.

## 프로젝트 카드 (STAR-I)

`inventory/_TEMPLATE.md`를 복사해 작성한다. 각 섹션의 의미:

- **S 상황**: 왜 이 일이 필요했나. 문제/불편/요구가 무엇이었나.
- **T 과제**: 내게 주어진(또는 스스로 정한) 목표. 성공 기준이 있었다면 명시.
- **A 행동**: 내가 실제로 한 일. 팀 작업이면 **나의 역할과 기여 비중**을 분리해서 기록.
  사용한 도구·기술·방법을 구체적으로.
- **R 성과**: 정량(숫자)과 정성(평가·변화)을 분리. 숫자가 없으면 아래 정량화 가이드로 추정.
- **I 증빙**: 숫자의 근거(산출 방식), 산출물 위치, 받은 평가·표창. 면접에서 "그 숫자 어떻게 나왔죠?"에 답할 수 있어야 한다.
- **한 줄 요약**: "[행동]하여 [성과]를 달성" 형태. 자소서 두괄식 첫 문장 후보.

## 성과 정량화 가이드

숫자가 없다고 성과가 없는 게 아니다. 아래 축으로 추정하되, 추정 근거를 I 섹션에 남긴다:

| 축 | 질문 | 예시 |
|----|------|------|
| 시간 | 전에는 얼마나 걸렸고 지금은? × 빈도 × 인원 | "월 8시간 × 12개월 = 연 96시간 절감" |
| 규모 | 처리 건수, 대상 인원, 예산 규모 | "직원 120명 대상", "연 3,400건 처리" |
| 품질 | 오류·재작업·민원이 얼마나 줄었나 | "반려율 15%→3%" |
| 최초성 | 조직에서 처음 시도한 것인가 | "부서 최초 자동화 도입" |
| 파급 | 다른 부서·후임이 이어받아 쓰는가 | "타 부서 2곳 확산" |

과장은 금지 — 근거를 댈 수 없는 숫자는 쓰지 않는다. "약", "추정" 표기는 허용.

## 인터뷰 진행법

사용자가 "정리를 못하겠다"고 하는 이유는 기억이 연대기가 아니라 사건 단위로 저장돼 있기 때문이다.
그래서 빈 템플릿을 주고 채우라고 하면 실패한다. 반드시 대화로 끌어낸다:

1. **연대기 스캔** (5분): 연도별 소속·직무만 훑는다. 상세로 들어가지 않는다.
2. **프로젝트 발굴**: `references/question-bank.md`의 발굴 질문으로 카드 후보를 목록화한다.
   이 단계에서는 제목만 수집 — 한 후보를 깊이 파기 시작하면 다른 기억 인출이 막힌다.
3. **카드 심화**: 후보 중 성과가 커 보이는 것부터 카드 1장씩 완성한다.
   한 번에 1장씩, S→T→A→R 순서로 질문. 숫자가 안 나오면 정량화 가이드의 질문으로 추정을 돕는다.
4. **세션당 2~3장이 한계** — 사용자가 지치면 카드 status를 `draft`로 두고 다음 세션에 이어간다.

## 원장 뷰어 (비공개 열람 페이지)

카드의 원천은 항상 마크다운 파일이다. 열람 편의를 위한 `inventory/ledger.html`은
**생성물**이며 직접 수정하지 않는다 — 카드를 추가·수정할 때마다 재생성한다:

```powershell
python "{이 스킬 경로}\scripts\build_ledger.py" "{프로젝트}\inventory"
```

ledger.html은 `site/` 밖에 있으므로 github.io 배포 대상이 아니다(비공개).
`[인터뷰 필요]`/`[확인 필요]`/`[마스킹 확인]` 표기는 뷰어에서 하이라이트되므로,
카드에 빈칸이 생기면 반드시 이 표기로 남긴다 — 다음 인터뷰의 할 일 목록이 된다.

## 갭 분석 페이지 (무엇을 더 채워야 하나)

"카드에 뭐가 부족해?", "내가 뭘 더 채워야 하지", "빈칸 점검", "STAR-I 관점에서 점검해줘", "갭 분석" 요청 시 만든다.
인터뷰를 한꺼번에 몰아서 하려는 사용자에게 **질문 목록을 먼저 보여 주는** 도구다.

```
inventory/P*.md → (Claude가 전수 점검) → inventory/gap.yaml → scripts/build_gap_report.py → inventory/gap_report.html
python3 .claude/skills/career-inventory/scripts/build_gap_report.py .
```

1. **카드를 전부 끝까지 읽는다.** 섹션별 분량만 세지 말고 "내가 만든 것·내가 내린 판단"이 있는지 본다.
2. 카드마다 S·T·A·R·I를 **0 빈약 / 1 보통 / 2 충분**으로 매긴다. 기준: S 왜 필요했는지와 당시 제약, T 목표치·기한·지시인지 자발인지,
   A 나·팀·외주의 분담선과 산출물 이름·도구, R 숫자의 산출 주체와 before/after·이후 쓰임, I 문서명·링크·확인해 줄 수 있는 근거.
3. 카드마다 **구체적인 질문 3~8개**를 쓴다(`sec`으로 어느 섹션을 채우는지 표시). "더 자세히"가 아니라 "플랫폼에서 내가 기획한 기능을 이름으로 3개"처럼 답이 명사로 나오게 쓴다.
   이미 제출한 지원서에 쓴 문장의 근거가 카드에 없으면 그 질문을 맨 위로 올린다. `priority` 1(먼저)~4.
4. 질문의 세 상태: 답을 들었으면 `answer:`에 한 줄 요약(=답함), 자료로만 확인되면 `wait: true`(=자료 대기), 둘 다 없으면 남음.
   **질문의 순서는 바꾸지 않는다** — 브라우저 메모가 "카드 ID + 순번"으로 저장된다. 새 질문은 끝에 붙인다.
5. `new_cards`에 카드로 만들 만한 후보(제출본에 썼는데 카드가 없는 것, 큰 카드에서 떼어 낼 사업 단위, 공개 저장소·성적표에서 보이는 프로젝트),
   `materials`에 찾아올 자료의 종류, `changes`/`remaining`/`next`에 달라진 것·남은 간격·다음 순서를 적는다.
6. 빌드 후 렌더를 확인한다. 사용자는 남은 질문의 메모 칸에 적고 **답변 전체 복사**로 내보낸다 → 받은 답은 카드에 반영하고 gap.yaml의 해당 질문에 `answer:`를 단다.

gap.yaml 양식과 예시는 `assets/gap_template.yaml`. 대외비 원문은 가져오지 말라는 반출 주의는 페이지에 항상 들어간다.

## 카드 작성 형식 규칙

**한 항목·한 문단 = 한 줄.** 긴 문장을 줄바꿈+들여쓰기로 이어 쓰지 않는다 —
에디터/뷰어에 따라 문장이 중간에 끊기거나 어색한 공백이 생긴다. 줄이 길어져도
에디터의 word wrap에 맡긴다. 새 줄은 새 항목(`- `)이나 새 문단일 때만 만든다.

## 카드 상태 관리

frontmatter의 `status`: `draft`(작성 중) → `confirmed`(사용자 확인 완료).
자소서·포트폴리오에는 `confirmed` 카드만 사용한다. draft 카드가 남아 있으면
산출물 생성 전에 사용자에게 확인을 요청한다.
